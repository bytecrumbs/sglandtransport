# M3 — SwiftData mirror + refresh + queries

**Status:** ⬜ Pending
**Depends on:** M2

## Goal

Reproduce the local network mirror (the core architectural decision — see ADR-0001) in SwiftData:
cache all bus stops/services/routes, refresh on a 30-day cycle, and serve the same queries the
Flutter `AppDatabase` exposes — including the direction-via-destinationCode derivation.

## Scope

- [ ] `@Model` entities mirroring `lib/src/database/tables.dart`:
  - [ ] `BusStop` (busStopCode, roadName, description, latitude, longitude).
  - [ ] `BusService` (serviceNo, operator, direction, category, origin/destinationCode, AM/PM
        peak/offpeak freq, loopDesc?).
  - [ ] `BusRoute` (serviceNo, operator, direction, stopSequence, busStopCode, distance, WD/SAT/SUN
        first/last bus).
- [ ] `ModelContainer` setup + an `@Observable` store wrapper; background `ModelContext` for bulk writes.
- [ ] **Refresh** (port `database.dart` `migration.beforeOpen`): on first launch or when
      `refreshDateKey` is past, clear + repull all three datasets via the paged loops
      (stops 0→5000, services 0→500, routes 0→26000, step 500), then set next refresh **30 days** out.
      Preserve the **out-of-cycle bus-services refresh** flag behavior.
- [ ] Progress reporting to drive the loading UI (port `db_init_notifier.dart`: per-dataset status +
      percent). Consumed by the Nearby loading state in M5.
- [ ] Queries (port `database.dart`) — note the **direction derived from `serviceNo` +
      `destinationCode`** done as a first fetch, then used to filter (two-step where Drift used a
      subquery):
  - [ ] `getBusStops(codes)`, `findBusStops(term)` (description/code/roadName), `getAllBusStops`.
  - [ ] `getBusServicesForBusStopCode(busStopCode, serviceNo?)`.
  - [ ] `getBusService(serviceNo, destinationCode)`.
  - [ ] `getBusRoute(serviceNo, busStopCode, destinationCode)` → stops with `stopSequence ≥ current`,
        joined to stop info, ordered by sequence; keep the "reload routes if empty" guard.
- [ ] Seeded store for `-uiTestStubMode` (fixed dataset) so M5/M6 UI tests are deterministic.

## Risks

- **Bulk insert of ~26k routes** — batch and benchmark first-launch time vs. Flutter; if it regresses,
  use chunked background inserts (or raw SQLite under the store).
- Two-step direction queries — cover with fixture-based unit tests.

## Verification

- First launch populates ~31.5k rows; loading UI shows per-dataset progress.
- Query unit tests pass on fixture data: direction derivation, route ordering + `≥ current` slice,
  search matching, services-for-stop.
- 30-day + out-of-cycle refresh logic unit-tested with an injectable clock.
